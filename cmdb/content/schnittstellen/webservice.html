Webservice (Generic Interface)¶

Über das Generic Interface lassen sich Config Items von außen lesen, suchen, anlegen, ändern und löschen (OTOBO als Provider) — und OTOBO kann Änderungen an Config Items an andere Systeme melden oder Config Items von dort abholen (OTOBO als Requester). Eingerichtet wird das unter Admin → Webservices.

OTOBO 11.1

Operationen, Invoker und ihre Einstellungen sind in 11.1 unverändert.

Operationen (OTOBO als Provider)¶

Operation

Zweck

Recht

ConfigItem::ConfigItemGet

Config Items mit allen Feldern lesen

ro

ConfigItem::ConfigItemSearch

Config Items suchen, liefert IDs

ro

ConfigItem::ConfigItemUpsert

Config Items anlegen oder aktualisieren

rw

ConfigItem::ConfigItemDelete

Config Items löschen

rw

Bemerkung

OTOBO 11.0 hat keine getrennten Operationen ConfigItemCreate und ConfigItemUpdate mehr — beides erledigt ConfigItemUpsert. Die mitgelieferte Beispielkonfiguration GenericConfigItemConnectorSOAP.yml verwendet noch diese alten Operationen und lässt sich deshalb nicht unverändert importieren.

Das benötigte Recht wird gegen die Berechtigungsgruppe der Klasse geprüft; es ist einstellbar unter GenericInterface::Operation::ConfigItemGet###Permission (und entsprechend für ConfigItemSearch, ConfigItemUpsert, ConfigItemDelete).

Anmeldung¶

Jede Anfrage enthält entweder UserLogin und Password eines Agenten oder eine SessionID. Alle Berechtigungsprüfungen laufen mit diesem Agenten.

Bemerkung

Die Einschränkung von Reitern über Groups in der Klassendefinition gilt für den Webservice nicht: Er liest und schreibt alle Felder der Klasse.

ConfigItemGet¶

Liefert die aktuelle Version eines oder mehrerer Config Items.

ConfigItemID (Pflicht)

Eine ID, mehrere IDs durch Komma getrennt oder eine Liste.

Attachments

1 = Anhänge base64-kodiert mitliefern. Standard: 0.

{
  "UserLogin": "api-cmdb",
  "Password": "…",
  "ConfigItemID": "32,33",
  "Attachments": 1
}

Antwort (gekürzt):

{
  "ConfigItem": [
    {
      "ConfigItemID": 32,
      "Number": "1038000032",
      "Name": "Notebook Mustermann",
      "Class": "Computer",
      "DeplState": "Production",
      "InciState": "Operational",
      "CurDeplState": "Production",
      "CurInciState": "Operational",
      "VersionID": 118,
      "DynamicField_ITSMModel-SerialNumber": "PF3K9X",
      "Attachment": [ { "Filename": "Lieferschein.pdf", "ContentType": "application/pdf", "Content": "JVBERi0…" } ]
    }
  ]
}

  • Ältere Versionen lassen sich nicht abfragen.

  • Dynamische Felder stehen als DynamicField_<Name> mit ihrem gespeicherten Wert — bei Referenz- und Auswahlfeldern also mit IDs bzw. Schlüsseln.

  • Fehlt das Recht auf eines der angefragten Config Items, schlägt die ganze Anfrage fehl.

ConfigItemSearch¶

Liefert eine Liste von ConfigItemID.

Suchparameter (jeweils Wert oder Liste): ConfigItemID, Number, Name, Classes, ClassIDs, DeplStates, DeplStateIDs, CurDeplStates, CurDeplStateIDs, InciStates, InciStateIDs, CurInciStates, CurInciStateIDs, CreateBy, ChangeBy.

Zeitfilter: ConfigItemCreateTime… und ConfigItemLastChangeTime… mit den Endungen OlderMinutes, NewerMinutes, OlderDate, NewerDate.

Dynamische Felder mit den Operatoren Empty, Equals, Like, GreaterThan, GreaterThanEquals, SmallerThan, SmallerThanEquals:

{
  "UserLogin": "api-cmdb",
  "Password": "…",
  "Classes": ["Computer", "Server"],
  "DeplStates": "Production",
  "DynamicField_ITSMModel-Manufacturer": { "Equals": "Lenovo" },
  "Limit": 100
}

Antwort:

{ "ConfigItemID": [32, 33, 57] }

  • Klassen, die der Agent nicht sehen darf, werden stillschweigend ausgelassen.

  • Ohne Treffer ist die Antwort leer.

  • Standardwerte: GenericInterface::Operation::ConfigItemSearch###SearchLimit (500), …###SortBy::Default (Age), …###Order::Default (Down). Ein Limit in der Anfrage ersetzt den Standardwert.

ConfigItemUpsert¶

Legt Config Items an oder aktualisiert sie. ConfigItem ist ein Objekt oder eine Liste von Objekten.

{
  "UserLogin": "api-cmdb",
  "Password": "…",
  "ConfigItem": [
    {
      "Class": "Computer",
      "Name": "Notebook Mustermann",
      "DeploymentState": "Production",
      "IncidentState": "Operational",
      "DynamicField_ITSMModel-SerialNumber": "PF3K9X",
      "DynamicField_ITSMModel-Manufacturer": "Lenovo",
      "Attachment": [
        { "Filename": "Lieferschein.pdf", "ContentType": "application/pdf", "Content": "JVBERi0…" }
      ]
    }
  ]
}

Antwort:

{ "ConfigItem": [ { "ConfigItemID": 32, "Name": "Notebook Mustermann" } ] }
Pflichtangaben je Config Item

Class, DeploymentState, IncidentState — jeweils als Name. Beim Anlegen zusätzlich Name (sofern die Klasse kein Namensmodul hat); fehlt er, wird das Config Item übersprungen.

Dynamische Felder

Direkt im Objekt als DynamicField_<Name> (Text oder Liste). Das Feld muss zur Klasse gehören; der Wert wird geprüft. Referenzfelder werden über ihren Externe-Quelle-Schlüssel aufgelöst (siehe Referenzfelder auf Config Items), ohne diesen als ID.

Anhänge

Attachment mit Filename, ContentType und base64-kodiertem Content.

Warnung

Werden Anhänge mitgeschickt, ersetzen sie alle vorhandenen Anhänge des Config Items.

Identifikatoren — anlegen oder aktualisieren?¶

Woran ein bestehendes Config Item erkannt wird, wird je Klasse in der Konfiguration der Operation festgelegt (Admin → Webservices → Operation bearbeiten). Zur Wahl stehen Number, ConfigItemID, Name, Classes, DeplStates und dynamische Felder; vorausgewählt ist Number.

  • Genau ein Treffer → Aktualisieren (Recht rw auf das Config Item).

  • Kein Treffer → Anlegen (Recht rw auf die Klasse).

  • Mehrere Treffer → das Config Item wird übersprungen.

  • Klassen ohne Identifikator werden übersprungen.

GenericInterface::Operation::ConfigItemUpsert::Classes begrenzt, für welche Klassen der Dialog überhaupt Identifikator-Felder anbietet (ab Werk aus = alle).

Warnung

Die Identifikatoren werden intern unter der ID der Klasse gespeichert (Identifier<KlassenID>). Wird eine Webservice-Konfiguration auf ein anderes System übertragen, auf dem die Klassen andere IDs haben, passen die Identifikatoren nicht mehr und müssen neu gesetzt werden.

Versionen¶

Das Aktualisieren folgt den Versionsauslösern der Klasse (siehe Wann entsteht eine neue Version eines Config Items?) — mit einer Ausnahme:

Warnung

Referenz- und Lens-Felder werden erst nach dem Anlegen bzw. Aktualisieren direkt in die aktuelle Version geschrieben. Änderungen an diesen Feldern erzeugen über den Webservice nie eine neue Version, auch wenn sie als Versionsauslöser eingetragen sind.

ConfigItemDelete¶

ConfigItemID (Pflicht) — eine ID, mehrere durch Komma oder eine Liste. Jedes Config Item wird auf rw geprüft und gelöscht. Die Antwort nennt die gelöschten IDs:

{ "ConfigItemID": [32, 33] }

Warnung

Die Operation ist nicht atomar: Scheitert ein Config Item, bricht die Anfrage mit Fehler ab — die davor genannten Config Items sind aber bereits gelöscht. Löschen entfernt auch die Historie (siehe Arbeiten mit Config Items (Agenten)).

Invoker (OTOBO als Requester)¶

ConfigItem::ConfigItemCreate, ConfigItem::ConfigItemUpdate

Senden ein Config Item an ein Fremdsystem. Beide Invoker verhalten sich identisch; welcher wann auslöst, bestimmt allein das im Webservice konfigurierte Ereignis. Gesendet wird die aktuelle Version mit allen Feldern (lesbar aufbereitet) und den Anhängen.

ConfigItem::ConfigItemFetch

Holt Config Items von einem Fremdsystem ab und legt sie an oder aktualisiert sie — mit denselben Pflichtangaben und demselben Identifikator-Prinzip je Klasse wie ConfigItemUpsert. Die Antwort des Fremdsystems darf eine Liste, ein einzelnes Objekt oder ein Objekt mit dem Schlüssel ConfigItems sein. Die Klassen, für die Identifikatoren angeboten werden, begrenzt GenericInterface::Invoker::ConfigItemFetch::Classes. Der Abruf läuft mit Administratorrechten.

Ereignisse¶

Invoker lassen sich an diese Ereignisse von Config Items hängen (ITSMConfigItem::EventModulePost###9700-GenericInterface):

ConfigItemCreate, ConfigItemUpdate, VersionCreate, VersionUpdate, NameUpdate, DeploymentStateUpdate, IncidentStateUpdate, ConfigItemDelete, AttachmentAddPost, AttachmentDeletePost.

Tipp

Webservice-Invoker sind in OTOBO der einzige Weg, automatisch auf Änderungen an Config Items zu reagieren — Ticket-Benachrichtigungen und der Generic Agent kennen keine Config-Item-Ereignisse.

Zeitgesteuerter Abruf¶

Daemon::SchedulerCronTaskManager::Task###TriggerConfigItemFetch-01 bis -03

Rufen den Fetch-Invoker regelmäßig auf (vorbereitet alle 20 Minuten, ab Werk aus). In Params die Platzhalter für WebServiceName und Invoker durch die echten Namen ersetzen.

Einmalig von Hand:

bin/otobo.Console.pl Maint::WebService::TriggerConfigItemFetch <Webservice> <Invoker>

Der Webservice muss gültig sein und für den Invoker eine REST-Zuordnung haben.
